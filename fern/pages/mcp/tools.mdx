The `kinetk` MCP exposes three tools that map to the async-job lifecycle.

## `create_context_job`

Submit an async job. Pick `kind` by **what you want back**:

| `kind` | Needs | Returns — use when |
|---|---|---|
| `intelligence_records` | `query` + `limit` | The matching **content itself** — ranked posts/videos with platform, tags, engagement, similarity. Use when you want source material to read or cite. |
| `intelligence_signals` | `query` (only) | **Synthesized insight signals only** — LLM-written arbitrage takeaways (overall, tag-focused, narrative-focused). No raw content. Use when you want the analytical "so what". _The API accepts only `query` for this kind — any filters/options you pass are dropped client-side before submit._ |
| `campaign_brief` | `campaign` + `limit` | A finished, **persisted strategy brief** we generate (positioning, narratives, recommended creators, platform strategy, content angles) plus its context. Use when you want a ready-made written deliverable. |
| `llm_context` | `campaign` + `limit` | The raw assembled campaign **context bundle** (narratives, top tags, creators, representative content) with **no generated brief**. Use when *you* will write the strategy yourself — faster and cheaper than `campaign_brief` because it skips the generation step. |

**Rule of thumb:** a `query` → `intelligence_records` (content) or `intelligence_signals` (insights); a `campaign` → `llm_context` (you synthesize) or `campaign_brief` (we synthesize).

### Input

- `intelligence_records` and `intelligence_signals` require `query` (string).
- `campaign_brief` and `llm_context` require `campaign` (string — the campaign name).
- `intelligence_records`, `campaign_brief` and `llm_context` also require `limit` (integer, 100–50000) — how many records to retrieve. Jobs are billed per record, so there is **no default**: you choose the spend (`1000` is a sensible starting point). `intelligence_signals` does not accept `limit` (its scan size is server-fixed).

Filters and options apply to `intelligence_records`, `campaign_brief` and `llm_context`. `intelligence_signals` takes **only** `query` — its time window, scan size, platforms and query expansion are managed by the service, and the MCP drops any filters/options before submit so the call still succeeds.

| Field | Type | Default | Notes |
|---|---|---|---|
| `platforms` | `string[]` | all | E.g. `["TIKTOK", "INSTAGRAM"]` |
| `limit` | `number` | (required) | How many records to retrieve, 100–50000. Sent to the backend as-is — never defaulted by the MCP, because jobs are billed per record and the caller chooses the spend. |
| `window` | `"7d" \| "30d" \| "all"` | `"all"` (set by the MCP) | Time filter on `published_at`. The API **requires** an explicit window for these kinds; when you omit it, the MCP sends `"all"` (no time filter). |
| `expandQuery` | `boolean` | `true` (server default) | LLM query expansion (`intelligence_records` only) |
| `vectors` | `"all_media" \| string[]` | `"all_media"` | Which vector indexes the search fans out to |

### Returns

```json
{
  "jobId": "0190bd6f-1234-7abc-8def-9876543210ab",
  "kind": "intelligence_signals",
  "status": "queued",
  "fromCache": false
}
```

If the backend has a fresh cached run for this input, `status` is `succeeded` and `fromCache: true` — `get_context_job_result` returns in O(1) on the next call.

### Example agent prompt

> Use kinetk to submit an `intelligence_signals` job for `luxury watch culture 2026`.

## `get_context_job_status`

Cheap poll. Pass the `jobId` you got from `create_context_job`.

### Returns

```jsonc
// running
{ "jobId": "...", "kind": "intelligence_signals", "status": "running",
  "submittedAt": 1745859300000, "startedAt": 1745859302100 }

// completed
{ "jobId": "...", "kind": "intelligence_signals", "status": "completed",
  "submittedAt": ..., "startedAt": ..., "completedAt": 1745859315400 }

// failed
{ "jobId": "...", "status": "failed",
  "error": "embedding service failed (403): permission denied",
  "submittedAt": ..., "startedAt": ..., "completedAt": ... }
```

Status values: `queued | running | completed | failed`. Latency: ~300 ms — safe to poll every 2–5 seconds.

## `get_context_job_result`

Fetch the result. Defaults to the **slim envelope** (token-efficient).

### Inputs

| Field | Type | Default | Notes |
|---|---|---|---|
| `jobId` | string | (required) | From `create_context_job` |
| `verbose` | boolean | `false` | If `true`, returns the full untouched graph-service payload |

### Returns (slim envelope)

The envelope shape depends on `kind`:

```jsonc
// intelligence_records → the matching content items
{
  "jobId": "...", "kind": "intelligence_records", "status": "completed",
  "items": [
    {
      "id": "uuid",
      "platform": "TIKTOK",
      "title": "...",
      "description": "...",
      "tags": ["smartwatch", "fitness"],
      "similarity": 0.81,
      "engagement": { "views": 12500, "likes": 800, "shares": 40, "comments": 60 },
      "publishedAt": "2026-05-01T12:00:00.000Z",
      "creator": { "followerCount": 120000 }
    }
  ]
}

// intelligence_signals → insight signals only (no raw content)
{
  "jobId": "...", "kind": "intelligence_signals", "status": "completed",
  "query": "...",
  "insights": ["..."],
  "tagInsights": ["..."],
  "narrativeInsights": ["..."]
}
```

Creator identity (handle/display name) and source URLs are never returned; a
creator carries only a non-identifying `followerCount`.

### Returns (verbose)

Set `verbose: true` for the full untouched graph-service payload for the kind —
see the [API Reference](/api-reference) for the complete response shapes.

### Pending behavior

If the job is still `queued` or `running` when called, returns `{ "status": "pending" }` instead of erroring. Useful for agents that want to call `get_context_job_result` directly and back off on pending without a separate status check.

### Expired

If the job's TTL has passed (~24 h after completion), the API's `410` surfaces as a failed envelope (the API no longer reports the kind at that point):

```json
{ "jobId": "...", "kind": "unknown", "status": "failed", "error": "job result expired" }
```

Resubmit via `create_context_job` to recompute.

## Putting it together

A typical agent loop for `intelligence_signals`:

1. `create_context_job({ kind: "intelligence_signals", query: "..." })` → `jobId`.
2. If `fromCache: true`, jump to step 4.
3. `get_context_job_status({ jobId })` every 3 s until `status: "completed"` (or `"failed"`).
4. `get_context_job_result({ jobId })` → slim envelope. Pass `verbose: true` for the full untouched payload (more tokens).

Most agents handle this entirely autonomously once you cue them with "use kinetk."
