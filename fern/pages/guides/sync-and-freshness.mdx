---
title: Sync & Freshness
description: How data lands in the Graph Service, how fresh each part is, and how windows filter it.
---

The Graph Service is read-only for you: you query it; you don't push to it. Underneath, an hourly ingestion pipeline pulls new and updated content from KINETK's scanning systems into the canonical store, and scheduled jobs rebuild the narrative and pattern maps on top of it.

## How fresh is each part?

| Data | Refreshed | Read by |
|---|---|---|
| Content | Hourly ingestion | `POST /search`, every job kind |
| Narrative map, `7d` | Every 6 hours | `GET /narratives/*`, `POST /search` |
| Narrative map, `30d` | Daily | `GET /narratives/*`, `POST /search`, `insights` corpus evidence |
| Pattern map | Weekly rebuild, topped up every 48 hours | `GET /intelligence/patterns/*`, `patterns` jobs |

`POST /search` and the async jobs retrieve over live content, so they see new posts as soon as they are ingested. The narrative and pattern reads return the latest rebuild.

## Checking freshness: `GET /health`

```bash
curl -H "x-api-key: $API_KEY" "$API_BASE/health"
```

```json
{
  "status": "ok",
  "db": "connected",
  "dbWriter": "connected",
  "sync": { "lastRunAt": "2026-10-05T17:32:11.000Z", "minutesSinceLastRun": 24, "isStale": false },
  "narratives": { "lastRunAt": "2026-10-05T12:00:03.000Z", "minutesSinceLastRun": 356, "isStale": false },
  "content": { "lastMigratedAt": "2026-10-05T17:32:11.000Z", "minutesSinceMigration": 24, "isStale": false },
  "timestamp": "2026-10-05T17:56:40.000Z"
}
```

- `sync` — the last content ingestion run.
- `narratives` — the last narrative map rebuild.
- `content` — the newest content in the store.
- `isStale: true` on any of them means that part is behind schedule.

`/health` returns `200` when everything is reachable and fresh, and `503` with the same body when something is unreachable or stale — so it works directly as an uptime probe.

## Windows

`window` restricts results by publish date:

| Value | Meaning |
|---|---|
| `24h` | Last 24 hours |
| `7d` | Last 7 days |
| `30d` | Last 30 days |
| `all` | No time filter |

Which windows each endpoint accepts:

| Endpoint | Windows | Default |
|---|---|---|
| `GET /narratives/*` | `7d`, `30d` | `7d` |
| `POST /search` | `7d`, `30d`, `all` | `30d` |
| `records`, `insights` jobs | `7d`, `30d`, `all` | required — no default |
| `stats` job | `24h`, `7d`, `30d`, `all` | `all` |
| `patterns` job, `GET /intelligence/patterns/*` | no window — the map covers the corpus's recent history | — |

**`window` never changes the price** — it chooses what to retrieve over, not what it costs. A bounded window returns fresher, more focused evidence; `all` is the right choice when the topic is long-running or the recent volume is thin. Bounded windows leave out content with no publish date.
