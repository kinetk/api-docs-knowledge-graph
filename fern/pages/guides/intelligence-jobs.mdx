All heavy intelligence work runs through one async endpoint pair:

- `POST /intelligence/jobs` — submit a job, get a `jobId` immediately.
- `GET /intelligence/jobs/{id}` — poll status; once `succeeded`, `intelligence_records` responses carry a presigned download URL, and all other kinds carry the result inline.

This page covers the lifecycle, the four supported `kind` values, the cache + dedup semantics, and the failure modes.

## Why async

The intelligence pipeline does real work: text embeddings, multimodal vector search fan-out, relational joins, KMeans clustering, two LLM calls. Typical end-to-end latency is 5–20 seconds. The synchronous API path caps at ~29 seconds, so heavy work runs async — submit returns in under 500 ms, and the worker has a 5-minute budget.

## Supported kinds

| `kind` | Input | Output | Cache window |
|---|---|---|---|
| `intelligence_records` | `query` + filters | The matching content items (downloaded via presigned URL) | 15 min |
| `intelligence_signals` | `query` only | Insight signals only — LLM arbitrage lines | 1 h |
| `campaign_brief` | `campaign` object | Persisted LLM-generated brief | 6 h |
| `llm_context` | `campaign` object | Raw campaign context bundle (no generated brief) | 6 h |

`intelligence_records` / `intelligence_signals` take a free-text `query`. `campaign_brief` / `llm_context` take a structured `campaign` object — see the [API Reference](/api-reference) for full shapes.

`intelligence_signals` accepts **only** `query` — every other parameter (time window, scan size, platforms, query expansion) is fixed by the service for this kind, and any extra input field returns `400`.

Input filters for the other three kinds (`intelligence_records`, `campaign_brief`, `llm_context`):

- `platforms`: e.g. `["TIKTOK", "INSTAGRAM"]`. Defaults to all.
- `window`: `7d | 30d | all`. **Required** — there is no default; omitting it returns 400. Use `all` for no time filter. A `24h` window is coming soon.
- `limit`: the number of records to retrieve, `100`–`10000`. **Required** — there is no default; omitting it returns 400, and a value above `10000` returns 400. Jobs are billed per record, so the limit is how you choose your spend (`1000` is a sensible starting point).
- `expandQuery`: opt in to LLM-backed query expansion (`intelligence_records` only).

## Submit response shapes

A submit can return one of three things depending on dedup + cache state:

```jsonc
// 1. Fresh — new work queued, credits reserved at the estimate
HTTP 202
{ "jobId": "...", "status": "queued", "estimated_cost": 1.333, "statusUrl": "/intelligence/jobs/..." }

// 2. Dedup — identical input already running, same jobId
HTTP 202
{ "jobId": "...", "status": "queued", "dedup": true, "statusUrl": "..." }

// 3. Cache hit — for intelligence_signals / campaign_brief / llm_context: inline result
HTTP 200
{ "jobId": "...", "status": "succeeded", "result": { /* full payload */ }, "fromCache": true, "charged": 1.2 }

// 3b. Cache hit — for intelligence_records: download envelope (never inline)
HTTP 200
{
  "jobId": "...", "kind": "intelligence_records", "status": "succeeded",
  "fromCache": true, "charged": 1.2,
  "actualRecordsReturned": 4812,
  "resultUrl": "https://...",
  "resultBytes": 18234567,
  "resultExpiresAt": 1781120190
}
```

Always check the HTTP status (`200` vs `202`) and the optional `fromCache` / `dedup` flags before deciding whether to start polling.

## Billing & costs

Jobs are paid in credits:

- **Submit reserves, completion settles.** A fresh `202` includes `estimated_cost` — an upper bound computed from your requested `limit` and `window`, reserved at submit. The final charge is computed from the records actually returned (≤ the estimate) and the unused remainder is released. Cache hits (`200`) are charged at the full rate — the body's `charged` field is the cost.
- **Insufficient balance → `402`.** The body includes `credits_required`, `credits_available` and a machine-readable recommendation: the largest affordable `limit` for your window, and (for `intelligence_records`) per-window alternatives so you can trade freshness for volume.
- **Headers.** Every billed response carries `X-Kinetk-Credits-Used` (this call) and `X-Kinetk-Credits-Remaining` (your balance).
- **`intelligence_signals` is flat-priced**: 0.5 credits per request for a fixed 3000-record scan. If the run matches fewer than 1500 records, the job fails (poll shows `status: "failed"` with a refine-your-query message) and the 0.5 credits are refunded in full.
- **Failed jobs are fully refunded.** Any job that ends `failed` releases its entire reservation.

## Polling

```bash
curl -H "x-api-key: $API_KEY" "$API_BASE/intelligence/jobs/$JOB"
```

Poll every 2–5 seconds. Status flows: `queued` → `running` → `succeeded` | `failed`.

The response shape on `succeeded` differs by kind:

### `intelligence_signals`, `campaign_brief`, `llm_context` — inline result

```jsonc
// running
{ "jobId": "...", "kind": "intelligence_signals", "status": "running",
  "submittedAt": 1745859300, "startedAt": 1745859305 }

// succeeded — result is inline
{ "jobId": "...", "kind": "intelligence_signals", "status": "succeeded",
  "submittedAt": 1745859300, "startedAt": 1745859305, "completedAt": 1745859318,
  "charged": 0.5,
  "result": { /* signals payload — see API reference */ } }
```

### `intelligence_records` — download envelope

Records results are **never** returned inline. When a records job succeeds, the response carries a presigned S3 download URL instead:

```jsonc
// succeeded — download envelope (no inline result)
{
  "jobId": "...", "kind": "intelligence_records", "status": "succeeded",
  "submittedAt": 1745859300, "startedAt": 1745859305, "completedAt": 1745859490,
  "charged": 12.5,
  "actualRecordsReturned": 4812,
  "resultUrl": "https://kinetk-intelligence-job-results-….amazonaws.com/jobs/<jobId>.json?X-Amz-…",
  "resultBytes": 18234567,
  "resultExpiresAt": 1745860390
}
```

Download the result with a plain GET — no `x-api-key` header, the URL is self-authenticating:

```bash
curl -o result.json "$RESULT_URL"
# or pipe directly into jq:
curl -s "$RESULT_URL" | jq '.content | length'
```

The downloaded object is JSON with `Content-Type: application/json`. Its shape is:

```jsonc
{
  "content": [
    {
      "id": "uuid",
      "platform": "TIKTOK",
      "title": "...",
      "description": "...",
      "tags": ["smartwatch", "fitness"],
      "similarity": 0.81,
      "engagement": { "views": 12500, "likes": 800, "shares": 40, "comments": 60 },
      "publishedAt": "2026-05-01T12:00:00.000Z",
      "creator": { "followerCount": 120000 }
      // ... additional fields per API reference
    }
    // ... more items
  ],
  "query": "smart watch launch",
  "window": "30d",
  "graph": { /* graph metadata */ },
  "retrieval": { /* retrieval stats */ }
}
```

Creator identity (handle/display name) and source URLs are never present; a creator carries only a non-identifying `followerCount`.

#### URL semantics — read before caching

- **15-minute expiry.** `resultExpiresAt` is a Unix timestamp (seconds). The URL stops working after that.
- **Fresh URL on every poll.** A new presigned URL is minted each time you call the status endpoint. The URLs differ across polls — **do not cache the URL**. Cache the downloaded JSON instead, keyed by `jobId` + `completedAt`.
- **On `403` from S3:** the URL expired between your poll and your download. Re-poll the status endpoint for a fresh `resultUrl`, then download again.
- **`resultBytes`** tells you the byte size of the object before you fetch. Use it to pre-allocate buffers or show download progress.

### `failed`

```jsonc
{ "jobId": "...", "kind": "intelligence_records", "status": "failed",
  "submittedAt": 1745859300, "startedAt": 1745859305, "completedAt": 1745859350,
  "error": "job exceeded the maximum processing time; reduce limit or narrow the window" }
```

Status response codes:

| Status | Body |
|---|---|
| `200` | Any job state (`queued` / `running` / `succeeded` / `failed`) |
| `404` | `{ "error": "job not found" }` — wrong `jobId` |
| `410` | `{ "error": "job result expired" }` — job is older than its TTL (~24 h after completion) |

## Cache semantics

Submit computes `inputHash = sha256(canonicalJson({ kind, input }))` and checks for a recent successful job with the same hash. If one exists within the per-kind freshness window above, the cached result is returned synchronously (status `200`, `fromCache: true`) — charged at the full rate. For `intelligence_records` cache hits, the response is the download envelope (not inline). To get fresher data, vary the input (e.g. a different `window`) or wait for the freshness window to lapse.

## Dedup semantics

Two **concurrent** identical submits will both hit the dedup check. The first creates a row and enqueues; the second observes the `queued`/`running` row and returns the same `jobId` with `dedup: true`. No second SQS message is sent — both pollers converge on the same result.

There's a small race window where two submits arriving in the same millisecond can both miss the dedup check and both queue. In that case both jobs run independently and produce identical results — the cost is duplicate work, not data corruption. This is documented as a v1 accepted trade-off.

## TTL

Job rows are deleted from DynamoDB ~24 hours after completion. After that, `GET /intelligence/jobs/{id}` returns `410 { "error": "job result expired" }`. Persist anything you need long-term on your side — for `intelligence_records`, that means saving the downloaded JSON, not the `resultUrl` (the URL expires in ~15 minutes).

## Using the MCP instead

If polling-loop boilerplate is a pain — especially inside an AI coding agent — install the `kinetk` MCP server. It exposes three tools that wrap the same flow:

- `create_context_job` → `POST /intelligence/jobs` (handles cache hit, dedup, retries)
- `get_context_job_status` → cheap poll
- `get_context_job_result` → slim or verbose envelope; fetches the `resultUrl` automatically for `intelligence_records`
