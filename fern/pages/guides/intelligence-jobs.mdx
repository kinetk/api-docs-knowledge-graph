title: Intelligence Jobs
description: The async job lifecycle — the four kinds, their inputs, submit, poll, cache and dedup.
---

Deep retrieval and analysis run through one async endpoint pair:

- `POST /intelligence/jobs` — submit a job and get a `jobId` back immediately.
- `GET /intelligence/jobs/{id}` — poll its status; once it has `succeeded`, the response carries the result.

Jobs are async because they do real work — multimodal vector search across the corpus, relational joins, clustering and LLM passes — that can take from about ten seconds to a few minutes. Submit returns in well under a second; the job itself has up to 15 minutes.

For a quick, bounded answer in one synchronous call, use [`POST /search`](./search.mdx) instead.

## The four kinds

| `kind` | Returns | Use when | Price | Cache |
|---|---|---|---|---|
| `records` | Ranked content rows, plus a relationship `graph` | You want the matching posts themselves — hundreds to thousands of them. | $0.010 per record returned | 15 min |
| `insights` | Narratives with corpus trajectory and sentiment, tag/theme signals, platform opportunities | You want the analytical "so what" about a topic. | $0.015 per record analyzed (+$1.00 with `includeSignals`) | 1 h |
| `patterns` | Matching visual patterns from the pattern map, with a written summary | You want to know what content looks like and how visual themes connect. | $10.00 flat | until 00:00 UTC |
| `stats` | Exact totals: records, views, likes, comments, engagement — overall and per platform | You want to size a topic, not read it. | $5.00 flat | until 00:00 UTC |

See [Pricing & Credits](../getting-started/pricing.mdx) for holds, settlement and the `402` budget advice.

## Inputs

### `records`

| Field | Required | Notes |
|---|---|---|
| `query` | yes | Free text. Hashtags in the query (`#fitness`) are also used to widen recall by tag. |
| `window` | yes | `7d`, `30d` or `all`. |
| `limit` | yes | How many records to buy, 100–10,000. There is no default: you choose the spend. `1000` is a sensible start. |
| `platforms` | no | Any of `tiktok`, `instagram`, `reddit`, `pinterest`, `x`, `snapchat`. Defaults to all. |

### `insights`

| Field | Required | Notes |
|---|---|---|
| `query` | yes | Free text. |
| `window` | yes | `7d`, `30d` or `all`. |
| `limit` | no | How many records to analyze. Omit it for the default depth — **1,500 for `7d`, 3,000 for `30d` and `all`**. Pass a lower number to cap cost, or a higher one (up to 10,000) for more depth. You pay for records actually analyzed. |
| `includeSignals` | no | `true` adds LLM-written takeaways (`insights`, `tagInsights`, `narrativeInsights`) for +$1.00. Needs enough evidence: 375 analyzed records on `7d`, 750 on `30d`, 1,500 on `all`, or the job fails with a full refund. |
| `returnRecords` | no | Also return the top N evidence posts in `content`. Default `0` — narratives already carry their representative posts. |
| `includeGraphs` | no | Default `false`. `true` adds the graph views (`graph`, `narrativeGraph`, `tagGraph`, `contentGraph`) — much larger payload. |
| `platforms` | no | Defaults to all. |

### `patterns`

| Field | Required | Notes |
|---|---|---|
| `query` | yes | Matched against the whole pattern map. |
| `limit` | no | Patterns to return, default 8, max 25. |
| `includeProse` | no | Default `true`. `false` skips the written summary. |

No `window`: the pattern map covers the corpus's recent history as a whole. See [Pattern Intelligence](./pattern-intelligence.mdx).

### `stats`

| Field | Required | Notes |
|---|---|---|
| `query` | yes | Free text. |
| `window` | no | `all` (default), `30d`, `7d` or `24h`. Bounded windows exclude posts with no publish date. |
| `platforms` | no | Defaults to all. |

`stats` returns `{ query, window, total, platforms[] }` — an exact count over everything matching, not a ranked sample, so there is no `limit` and no content rows.

Any other field, or a value of the wrong type, is rejected with `400`.

## Submit

```bash
curl -X POST "$API_BASE/intelligence/jobs" \
  -H "x-api-key: $API_KEY" -H "content-type: application/json" \
  -d '{ "kind": "records", "input": { "query": "sustainable sneakers", "window": "30d", "limit": 1000 } }'
```

A submit returns one of three shapes:

```jsonc
// 1. New job — queued, credits held at the estimate
HTTP 202
{ "jobId": "…", "status": "queued", "estimated_cost": 10, "statusUrl": "/intelligence/jobs/…" }

// 2. Dedup — the same job is already queued or running; same jobId, nothing new held
//    (status is that job's real state: "queued" or "running")
HTTP 202
{ "jobId": "…", "status": "running", "dedup": true, "statusUrl": "/intelligence/jobs/…" }

// 3. Cache hit — a recent identical job's result, returned inline
HTTP 200
{ "jobId": "…", "status": "succeeded", "result": { /* full payload */ }, "fromCache": true, "charged": 9.4 }
```

Check the HTTP status (`200` vs `202`) before deciding whether to poll.

## Poll

```bash
curl -H "x-api-key: $API_KEY" "$API_BASE/intelligence/jobs/$JOB"
```

Poll every 2–5 seconds. Status flows `queued` → `running` → `succeeded` | `failed`. Most jobs finish in 10–40 seconds; `window: "all"` and large pulls commonly take 1–3 minutes. A long `running` is normal — allow up to about 5 minutes before treating a job as stuck.

```jsonc
// running
{ "jobId": "…", "kind": "insights", "status": "running",
  "submittedAt": 1745859300000, "startedAt": 1745859302100 }

// succeeded
{ "jobId": "…", "kind": "insights", "status": "succeeded",
  "submittedAt": 1745859300000, "startedAt": 1745859302100, "completedAt": 1745859315400,
  "result": { /* see the API Reference */ } }

// failed — the hold is refunded in full
{ "jobId": "…", "kind": "insights", "status": "failed", "error": "…" }
```

| Status | Meaning |
|---|---|
| `200` | The job, in any state. |
| `404` | No such job for your account. |
| `410` | The job expired — results are kept for about 24 hours after completion. |

### Large results — download link

Large results (typically big `records` pulls) are too big to return inline. The response then omits `result` and includes a short-lived download link instead:

```json
{
  "jobId": "01931f7e-…",
  "kind": "records",
  "status": "succeeded",
  "resultStorage": "s3",
  "resultUrl": "https://…",
  "resultBytes": 8200431,
  "resultExpiresAt": "2026-06-11T05:37:09.000Z"
}
```

If `result` is absent and `resultStorage` is `"s3"`, `GET` the `resultUrl` for the full JSON. The link lasts about an hour; if it has expired, poll the job again for a fresh one.

## Cache and dedup

- **Cache.** A submit identical to a recent successful job — same `kind` and same input — returns that job's result inline (`200`, `fromCache: true`) instead of running again. `records` and `insights` cache hits are charged at the full rate; `patterns` and `stats` are free to re-read for the account that paid, until 00:00 UTC. To get a fresh run, change the input or wait for the window to pass.
- **Dedup.** A submit identical to a job that is still `queued` or `running` returns that job's `jobId` with `dedup: true`. Nothing new runs and nothing new is held — just poll the same id.

## Keep the results

Jobs are deleted about 24 hours after they finish, after which `GET /intelligence/jobs/{id}` returns `410`. Store anything you need longer on your side.
